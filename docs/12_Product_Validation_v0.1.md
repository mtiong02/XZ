# 小知产品验证 v0.1

## 唯一目标

验证家庭用户是否愿意每天打开小知，并用它完成一次“今天怎么吃、缺什么”的决策。验证期不扩展开放式聊天、自动下单、复杂健康分析或新的内容模块。

## 每日核心闭环

1. 打开小知，看到今日需要处理的临期食材/提醒。
2. 直接说“今天吃什么”“几个人吃”“优先用快过期的”。
3. 小知基于家庭库存、用餐人数、健康目标和偏好生成具体菜单。
4. 用户确认菜单后，明确说“把缺的加入购物清单”。
5. 用户可以在页面编辑和确认，不要求记住模块入口。

## 最小 Agent 分层

- 确定性业务层：库存查询、库存写入、购物清单写入、提醒读写。
- 规则/context 层：食材单位、保存区域、临期优先级、人数份量、家庭禁忌。
- AI 推理层：只有需要组合、权衡或个性化时调用餐食 Agent；不能改变库存事实。
- 记忆与反馈层：区分家庭事实和可变偏好，记录推荐是否被接受/修改。
- 轮次协调层：同一家庭成员同一时间只有一个有效任务；结束后回到待机，必须重新唤醒。

## 里程碑 M1：今晚吃什么闭环（当前优先）

- `session_id → turn_id → task_id(voice_job_id)` 贯通 Web、API 和 Agent 事件。
- 同一家庭成员的新任务会取消旧任务；餐食 Tool 按任务单飞，旧计划不会覆盖新计划。
- `inventory.read`、`meal.recommend`、`shopping.confirm` 经过统一 Tool Executor；业务服务仍是唯一事实/写入边界。
- 家庭上下文包含成员限制、家庭偏好、在家模式和默认人数，并随餐食规划一起提供给 MiniMax。
- 一句话只产生一个最终菜单方案；不在本里程碑扩展开放式闲聊或自动下单。
- 事件记录 `PRODUCT_OPENED`、`FIRST_UTTERANCE`、`MEAL_FLOW_STEP`，用于按真实行为定位失败步骤。

## 验证指标

| 指标           | 定义                                      | 目标/判断                |
| -------------- | ----------------------------------------- | ------------------------ |
| 日打开家庭数   | `PRODUCT_OPENED` 去重家庭数               | 连续 7 天不下降          |
| 每日打开次数   | `PRODUCT_OPENED` 次数（按上海时区）       | 观察趋势，不预设阈值     |
| 首句分布       | 每个会话的 `FIRST_UTTERANCE`              | 找到最高频真实入口       |
| 失败步骤       | `MEAL_FLOW_STEP` 按 `metadata.step` 聚合  | 优先修复最高失败步骤     |
| 每周回访率     | 本周打开且上周也打开的家庭 / 上周打开家庭 | > 35% 进入下一轮         |
| 餐食方案生成率 | 有效餐食请求中生成方案的比例              | > 80%                    |
| 餐食接受率     | 明确接受方案的次数 / 方案生成次数         | > 50%                    |
| 菜单修改率     | 明确要求修改 / 方案生成次数               | 观察真实不满意点         |
| 菜单拒绝率     | 明确拒绝方案 / 方案生成次数               | 观察是否需要调整候选策略 |
| 购物草稿生成率 | 有缺料的方案中生成购物草稿的比例          | > 60%                    |
| 购物确认率     | 确认写入清单 / 购物草稿                   | > 50%                    |
| 任务失败率     | `VOICE_FAILURE` / 有效轮次                | < 10%                    |

`GET /api/v1/admin/validation-metrics?days=14` 提供事件聚合；接受率在当前版本先保留事件位，避免用“播报完成”冒充用户接受。

## 试点协议

- 招募 15–20 个真实家庭，连续使用 14–21 天。
- 第 0 天：记录家庭人数、常用食材、饮食限制和首次库存。
- 每天只观察核心闭环，不主动引导用户测试边缘功能。
- 每 3 天收集一次一句话反馈：“今天小知有没有帮你更快决定吃什么？”
- 记录原始对话时去除 token、手机号和精确住址；只保留任务结果与错误类型。
- 第 7 天和第 14 天各做一次复盘，按“保留/修复/暂停”决策，不按功能数量决策。

## 产品闸门

任何新功能必须回答：它是否让用户更容易决定今天吃什么，或更容易减少食材浪费？如果不能在试点指标中验证，暂不进入开发。
